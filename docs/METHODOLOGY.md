# 方法论：任务书驱动的多 CLI 协同闭环

> 本文是 quota-router 项目在八个 Sprint 中实测形成的**工作方法**，独立于插件代码存在。插件只是道具——这套方法可以用在任何"主控 AI + 多个本地 CLI"的组合上，不依赖本仓库的代码。

## 核心命题：复杂度放在哪一层

多 CLI 协同项目最容易死在同一个地方：**把编排逻辑写进代码**。任务状态机、重试循环、自动路由……插件越长越像一个微型 CI/CD 引擎，然后死于维护。

quota-router 的答案（Linus 式：插件是 userspace，别做成内核）：

```
复杂度放 markdown（任务书、路由表、验收协议）—— 改起来零成本，AI 和人都能读
插件只做管道（spawn / 截断 / 判成败）—— 越薄越稳，200-340 行/适配器
```

**插件八轮迭代没重构过一次；方法论每个 Sprint 都在进化。这就是分层的红利。**

## 闭环全貌

```
[需求] ──> [主控 AI 写任务书 TASKBOOK-*.md]
              │  含：白名单、基线 commit、反向验证、止损线
              ▼
        [便宜 CLI 拿任务书自建执行]  ←— 执行者角色
              │
              ▼
        [主控 AI 独立验收]          ←— 不信自述：复跑测试、查磁盘、暗卷抽查
              │
              ├─ 通过 ──> [第三方 CLI 对抗评审]  ←— 评审者角色（换一家，防同源盲区）
              │              │
              │              ├─ NO-GO ──> 修复 ──> 回到验收（循环直至 GO）
              ▼              ▼
        [合并、发版、记录契约发现到设计文档]
```

## 五个实测成立的实践

### 1. 任务书是唯一的任务来源

执行 CLI 拿到的任务是冻结的任务书（提交为 git 对象），不是会话上下文。任务书六要素，缺一个都会出事：

| 要素 | 作用 | 缺了会怎样 |
|---|---|---|
| **白名单** | 哪些文件能碰 | 执行者顺手改了不该改的，出事分不清是谁弄的 |
| **基线 commit** | 保护文件零 diff 可机器验证 | "GOAL.md 没动过"变成口头保证 |
| **反向验证** | 故意弄坏，证明防线会响 | 测试全绿但防线是摆设（注释掉 kill 逻辑应该看到挂起） |
| **止损线** | 连败 3 次换项 / 跑满 10 轮停 | 执行者在死胡同烧完预算 |
| **让步顺序** | 打架时谁赢（如"失败判断准确 > 超时能杀 > 代码好看"） | 执行者按自己偏好取舍 |
| **"我替领导拍的板"** | 悬而未决的决策显式记录（含代价） | 决策凭空出现，无人能追溯 |

实测中任务书本身错过一次（反向验证 2 在逻辑上不成立），执行者发现并在 PROGRESS.md 记录订正——**书是人写的，实测才是裁判**。这个原则连任务书自己也不例外。

### 2. 契约调研先于代码，顺序不许换

每接一个新 CLI，先在隔离 fixture 上实测（探针法：小任务 + md5 前后对比），重点测**失败时的形状**而不是成功时。三个真实例子：

- codebuddy 文档说失败会给 JSON——实测 API 层失败是 **exit 0 + 空 stdout**，照抄 cursor 的判法会把失败当成功
- agy 文档暗示 `--dangerously-skip-permissions` 能写文件——实测写工具被锁死在它自家目录，**任何权限档都写不了用户文件**（于是诞生了更安全的 apply 模式）
- codebuddy 的 `status`/`whoami` 看似探测命令——实测全部把参数当 prompt **跑真 LLM 会话烧 token**

调研结论全部落设计文档（本仓库为 GOAL.md），带"实测"或"官方文档"标注。**文档可以是错的，实测才是裁判**——本项目三次预判被实测推翻，全部记录在案。

### 3. 执行与评审角色分离，且换引擎

实测结论（三个候选执行者的沙箱行为各不相同）：

- **cursor 执行 + Codex 评审**是最佳组合
- Codex 的沙箱跑不了 fake-bin 测试套件（静默吞 spawn 输出）——所以它执行时任务书要写死"你的自检限于静态检查，测试归验收方"
- 但它的**对抗评审**极其锋利：三轮评审抓出三个真 blocker（CI 分支名不匹配、SUCCESS 空 response 误判、版本判据过松），两轮 NO-GO 全部命中
- 评审要对抗性：明确指示"找会在公开发布时难堪的问题"，不是"帮忙看看"

### 4. 验收协议：不信自述

执行者交付的总结一律不听信，验收方独立做三件事：

1. **复跑**：自己跑全量测试，对数字
2. **查磁盘**：`git diff <基线> -- <保护文件>` 必须为空，marketplace 只增不改
3. **暗卷**：执行者看不见的抽查——重放关键场景（如真实复现"部分成功陷阱"看 warning 弹不弹）、审代码是否真按契约（如 `close()` 回调连 code 参数都不接，物理上无法偷看退出码）

八轮验收没有一轮靠执行者自述过关。

### 5. 路由决策留在文档，不进代码

什么任务给哪个引擎，写在路由表（README）里由人或主控 AI 查阅执行，**不写成自动路由代码**。理由：路由依据是实测画像（谁快、谁稳、谁有坑），这些随上游版本漂移——改一行 markdown 和改一段路由代码的风险完全不同。

## 给复用者的最小清单

想在你的项目用这套方法，只需要：

1. 一个主控 AI 会话（Claude Code / 任何能写文件、跑命令的 agent）
2. 一个以上本地 CLI（headless 模式可调用）
3. 一份设计文档（记录契约调研，持续追加）
4. 按上面的六要素写任务书，交给 CLI 执行，你独立验收
5. 有条件就找第二个 AI 做对抗评审

不需要：抽象层、编排引擎、状态机、本仓库的任何代码。

## 已知边界

- 这套方法的生产物必须**可机器验证**（测试、diff、md5）——产出散文的任务不适用
- 多 CLI 契约会随上游漂移，设计文档是活文档，接入前重跑探针
- 执行者会真实修改文件：涉及写能力的任务，测试只对隔离 fixture 动手，仓库自身走白名单保护
